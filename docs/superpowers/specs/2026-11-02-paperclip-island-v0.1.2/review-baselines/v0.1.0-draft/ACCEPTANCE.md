# Paperclip Island 验收与协作闭环

版本：`paperclip-island-m0-spec-v0.1.0-draft`  
日期：2026 年 11 月 2 日  
状态：配套设计规则草案，待独立评审与用户批准  
适用范围：独立私有项目的 M0 mock-only 客户端，不授 M1、发布或 Mac 执行权限

## 1 证据原则

每条结论必须回答“谁、在哪个环境、针对哪些精确字节、运行了什么、得到什么结果”。口头完成、评论、任务创建、accepted、running、截图、单元测试和实机验收是不同状态，不互相替代。

结果只允许 `pass`、`fail`、`blocked`、`not_run`、`not_applicable`。后两种不是绿色；`not_applicable` 必须附范围依据，并经 reviewer 确认不能掩盖必需 gate。文档评审通过只能叫“设计评审通过”，模拟测试通过只能叫“mock 逻辑通过”。

GitHub 或其它平台页面上看不到检查，不等于通过或失败；未读取的日志、未知构建内容和没有绑定版本的截图不能补全证据。以实际 source commit/tree、构建产物 SHA-256、测试环境和日志为准。

## 2 授权与角色

| 角色 | 可做 | 不可推定 |
| --- | --- | --- |
| 用户 | 批准设计、范围、具体执行、合并、发行、权限及费用 | 一次回复不自动批准后续扩张 |
| 主协调者 | 在明确范围派单、核真实接收／run、汇总门禁、申请决策 | 无权靠超时抢锁、把旧项目权限移来或自动发布 |
| 唯一实现 owner | 在认领和锁定范围实现、保存成果、报告证据 | 不同时修改共享锁文件，不自我独立批准 |
| 独立 reviewer | 只读审精确版本、指出问题、验证证据和修复差异 | 不以自己的改代码代替独评；不凭未跑测试给绿 |
| 实机验收者 | 在单独获准的环境和窗口执行指定检查 | 不自行安装工具、扩权限、强杀、部署或接真实账号 |

同一自然人／agent 不能同时作为某改动的实现者与最终独立 reviewer。评审协助修改正文或代码后，应标记参与范围；相应区域需另一未参与者复核。模型名称不同不自动满足独立性，身份及参与记录才是证据。

## 3 认领 锁与停止交接

每次派单记录 `task_id`、owner、spec 版本及 hash、base commit、允许文件、语义范围、非目标、运行许可、结束条件和预期交付。只有真实收件与 accepted 后才称“已接单”，只有平台 run ID 和进度证据才称 running。

一个任务只有一个实现 owner。文件锁保护具体路径；语义锁保护状态契约、通知去重、窗口行为、凭据边界等跨文件责任。同名分支、不同目录或不同 agent 不能绕过语义锁。

需要改锁外内容时先停该部分，说明影响，等待协调者在用户批准范围内重新分配；禁止“顺手修”跨任务共享文件。评审只读无写锁，但不得改实现者成果。

停止交接必须列出：最后可信 commit/tree 或工作区文件 hash、dirty 文件和保留位置、已做／未做、命令及结果、活动进程／运行终态、未知动作、当前锁、后继范围。未能确认动作结果时标记 uncertain，先只读对账，不重复提交。没有交接回执不得宣称所有权已经转移。

超时、静默、离线、模型容量失败、任务 completed 或定时器到点都不自动释放语义锁。协调者可请求状态并暂停新派单；接管须核原 run 已终止及成果保全，并取得有效范围批准。

## 4 失败与有限修正

当前仅文档阶段，允许作者修正文档问题并重新生成摘要，不得因此开始实现。后续产品实现计划必须显式写出有限修正额度：建议允许 **一次** 同一授权任务内、同一文件／语义锁范围的确定性代码或测试缺陷修正及对应验证；这是待批准建议，不是现在生效的重试权。

首次失败先记录原命令、退出码、输出、已发生副作用和未决状态，暂停依赖该结果的后续步骤。不得通过删断言、跳过必须测试、放宽安全约束或换目标版本制造通过。

以下情况不适用普通代码修正额度：权限拒绝、凭据／认证问题、控制冲突、资源不足、外部计费、网络安全变更、安装失败或动作结果 uncertain。先只读诊断；需要新的具体授权时等待。拒绝后的再次尝试仅在实质性新证据说明原动作未执行且相关限制已合法解决时，最多一次；不通过改工具、改环境或换路径绕过同一限制。uncertain 必须先对账，时间流逝本身不是证据。

第二次确定性失败、范围变化或需要新依赖时，保存成果并报告下一最小决策，不自动循环。停止不是删除成果或放弃责任，后续仍由协调者跟进至用户明确处理。

## 5 设计冻结和版本绑定

设计使用人可读版本与字节摘要双绑定。本版本为 `paperclip-island-m0-spec-v0.1.0-draft`。`REVIEW_MANIFEST.json` 记录 SPEC、ACCEPTANCE、schema 的 SHA-256，不在文件内自嵌其自身 hash，避免循环。

独立评审须直接读取这些文件，而不是只读作者摘要。结论包含版本、各文件 hash、评审范围、发现等级、阻塞项及没有检查的部分。任何规范性修改均更新版本或 revision、重算 hash，并给出相对已评审基线的 diff SHA-256。旧 review 不自动覆盖新字节；纯排版修正也要记录差异，由 reviewer 判定是否仅需增量复核。

产品阶段同时绑定 repo、base/head commit、tree、规范化 diff hash、构建产物 hash、spec hash 与测试证据。这里的 diff hash 建议对保留的 `git diff --binary --full-index <base> <head>` 输出原始字节求 SHA-256；不凭手工摘要替代。尚无仓库／源码时字段为 null 且 subject.kind 为 design-only，不能填虚构 SHA。

## 6 状态机验收矩阵

以下均先用固定 fixture、可注入时钟和模拟通知／导航 sink 执行。每行都必须有独立断言及事件序列，不以截图替代逻辑测试。

| ID | 输入与起点 | 必须结果 | 不允许 |
| --- | --- | --- | --- |
| ST01 | 无 baseline 启动 | offline＋unknown；模拟标识、未加载原因 | 显示成功或已连接 |
| ST02 | baseline 含 running/succeeded/failed/unknown | 四种状态精确呈现；历史 failed 不提醒 | 把 baseline 当新失败 |
| ST03 | running → 新 failed 增量 | failed；符合规则时仅一次模拟提醒 | 仅依颜色区分 |
| ST04 | running → succeeded | succeeded，更新时间正确 | 制造失败提醒 |
| ST05 | unknown → running / succeeded / failed | 分别正确转换；新失败仅一次 | unknown 默认为成功 |
| ST06 | 重复 event_seq、revision 或消息重放 | 状态不变；通知不增；任务更新时间不伪刷新 | 每次收到都更新为“刚刚” |
| ST07 | 旧 event/revision/attempt 晚到 | 忽略；不覆盖新尝试 | 状态倒退 |
| ST08 | 同 attempt 终态后 running 或反向终态 | unknown＋source_conflict，等待新 baseline | 任选后到状态、误绿 |
| ST09 | failed 后更高 ordinal 的新 attempt | 新 running 可见；新 attempt 失败可再提醒一次 | 旧账本吞新失败 |
| ST10 | 同 ordinal 换 ID／同 ID 换 ordinal | 输入冲突明确，不能拼接 | 模糊合并 |
| ST11 | malformed 增量／未知枚举／缺 ID | 拒绝并保留可信值；诊断脱敏 | 崩溃或用 success 兜底 |
| ST12 | baseline 同键冲突或不完整 | 整体拒绝，不部分应用 | 混合新旧数据刷绿 |
| ST13 | 完整空 baseline | 暂无任务，不产生终态或通知 | 把消失任务记成功 |
| ST14 | disconnected | offline；保留旧任务＋时间＋过期提示 | running 改 failed |
| ST15 | 无合法成功输入超过 30 秒 | stale；不改变任务、不提醒失败 | 把阈值当任务超时 |
| ST16 | heartbeat 有效但任务未变化 | online；任务更新时间保持 | 把 heartbeat 当任务进展 |
| ST17 | reconnect 后旧回调、新 baseline | 旧 generation 丢弃；新 baseline 后才 online | 旧结果污染新视图 |
| ST18 | epoch 变化 | 重建 baseline；历史失败不回放 | 跨 epoch 共用游标 |
| ST19 | 墙钟倒退或跳进 | 事件按序号，freshness 按单调时钟 | 负年龄、乱序、重复提醒 |
| ST20 | 解析错误／无效 heartbeat | 不刷新成功时间，最终按阈值 stale | 无限显示 online |

## 7 提醒与入口验收

| ID | 场景 | 必须结果 |
| --- | --- | --- |
| NT01 | authorized＋首次新失败 | 模拟 sink 恰好一条；绑定 source/task/attempt |
| NT02 | 同失败重放、详情变更、面板重开 | 0 条新增提醒 |
| NT03 | denied / not_determined | 卡片内提示；0 次系统授权调用和投递；不反复询问 |
| NT04 | 拒绝后改 authorized | 旧 suppressed 失败不补发；后续新 attempt 可提醒 |
| NT05 | 通知返回 fail / uncertain | 记录结果，不自动重投 |
| NT06 | 应用重启且 baseline 有旧失败 | 不补发；新 live failure 另按规则 |
| NT07 | 不同 source 相同 task/attempt ID | 身份隔离，不错误去重 |
| NT08 | 有相同系统 identifier 的多次逻辑调用 | 应用账本阻止重复；不能靠系统 identifier 作为唯一防线 |
| LK01 | 点击卡片 | 只打开本地摘要详情，不发网络请求 |
| LK02 | 原任务未配置／不可达 | 原任务按钮禁用并有原因 |
| LK03 | fixture 含 file/javascript/custom scheme、跨 host 或带凭据目标 | 不导航；测试 sink 也标为拒绝 |
| LK04 | 详情反复开关、返回、切任务 | 正确绑定当前 task/attempt，不显示前一任务内容 |

真实系统通知另列 REAL-NOTIFY gate；M0 mock 的 authorized/denied 只是模拟状态，不能当作 macOS 通知授权、横幅显示或免打扰实测。

## 8 窗口 安全和资源验收

| ID | 场景 | 必须证据与结果 |
| --- | --- | --- |

| UI04 | 长标题、空摘要、Unicode、缩放、浅深色 | 文本可读、不裁掉关键状态；不用纯颜色表达 |

| RES02 | 环境资源不足、工具缺失、权限拒绝 | 原地停止；不清理、不安装、不杀进程、不切执行器绕过 |

UI01–UI05、SEC02 的 OS 行为和 RES01 需要获授权 Mac 实机证据。模拟窗口对象、快照图片或 Linux 测试最多覆盖逻辑部分。M0 不要求先安装未知工具来验证这些项目。性能数值预算在实现计划和可用实机明确后冻结；在冻结前不得宣称“低内存”或完整性能通过。

## 9 证据包

正式证据包遵循 `EVIDENCE.schema.json`。至少包括：

- 规格版本和 SPEC／ACCEPTANCE 文件 SHA-256；设计评审或代码验收 subject 类型。
- repo、base/head/tree/diff 与产物摘要；不存在时明确 null 和原因。
- run ID、操作者、起止时间、环境 ID、OS、CPU、SDK／工具链版本及权限范围。
- 每项 check 的 ID、实际方法、mock／静态／真实级别、结果、退出码、日志／截图引用与摘要。
- 屏幕证据仅使用虚构数据；截图需说明设备、分辨率、缩放、构建产物和实际步骤。
- 所有 blocked/not_run/uncertain、发现等级、责任人和下一最小条件；不得只交成功摘录。
- 独立 reviewer 身份、未参与声明、精确被审字节、问题清单和增量修复复核。
- gate 逐项状态，不设一个吞掉未知项的 overall_green。

不把秘密、完整私人路径、业务正文或真实账号截图写入证据包。工具输出必须保留能核验结果的必要内容，敏感字段只用脱敏说明且不谎称已独立验证被遮挡部分。完整原日志若需受限保留，记录受限位置与权限，不公开上传。

Schema 校验本身只证明结构符合，不证明测试真的执行。mock pass 不能满足 real-required gate；对引用文件还需检查存在、hash 一致及内容与声明相符。缺少任何绑定时相应 gate blocked。

## 10 Gate 和 Definition of Done

| Gate | 放行条件 | 当前状态 |
| --- | --- | --- |
| G0 设计完整 | SPEC、验收矩阵和 schema 自洽，版本／hash 固定 | 待独立评审 |
| G1 独立设计审查 | 未参与作者审阅精确字节；P1/P2 清除；未决明确 | not_run |
| G2 用户设计批准 | 用户批准最终版本及实施边界；仓库 owner/name 明确 | 未取得本设计批准 |
| G3 实施授权与认领 | 独立私有 repo、明确计划/锁/环境/运行额度/依赖范围 | not_run |
| G4 M0 逻辑 | 所有 ST/NT/LK mock 检查、输入边界及静态安全检查通过 | not_run |
| G5 macOS 构建 | 授权 macOS 环境，固定工具链；x86_64/arm64 构建与产物绑定 | not_run |
| G6 Mac 交互 | 获准实机 UI/安全/退出检查及截图；每架构覆盖单列 | not_run |
| G7 签名与交付检查 | 实际验证产物签名状态及声明；分发范围和许可明确 | not_run |
| G8 独立代码审查 | 精确 head/tree/diff；实现者之外 reviewer，无未解 P1/P2 | not_run |
| G9 用户验收／合并 | 用户看过证据和剩余限制，批准对应合并／交付 | not_run |
| REAL-NOTIFY | 另获通知与实机运行批准；实际允许/拒绝/勿扰证据 | M0 不执行，独立待验 |
| M1 真实只读 | 后端、身份、数据范围、网络入口及具体接口另批并实测 | 不在本次范围 |
| RELEASE 发布 | 单独发布批准、签名／公证／费用和回退方案 | 不在本次范围 |

M0 逻辑完成的 DoD 仅为 G4，并必须标记“mock-only”。M0 可交互原型完成需 G4–G8 对批准支持范围全部通过，且未通过架构不得宣传支持。若只有一个架构实机可用，报告该覆盖并请求用户决定收窄目标或继续等待，不能自己豁免另一架构。项目完整 M0 验收还需 G9；这仍不授权 M1 或发布。

P1：越权、凭据暴露、真实任务写入、隐式后台、错误版本交付等安全／数据问题。P2：错误终态、重复提醒、乱序污染、不可退出、关键平台声明无证据等实质功能／验收问题。P3：不影响边界的文案或视觉问题。P1/P2 必须关闭；P3 可由用户明确接受保留，不能改标签掩盖缺陷。

## 11 闭环流程

1. 作者产设计草案和 hash，独立 reviewer 只读审查。
2. 作者逐项回应问题，修正文档；新增字节重新绑定并增量复核。
3. 用户批准冻结设计及下一步范围；未批准则只继续必要澄清。
4. 编写实施计划，明确 repo/文件/语义锁、测试、环境和有限修正条件；获得实际派单许可。
5. 唯一 owner 实现并保存精确代码与全量结果；失败按第 4 节停止和交接。
6. 未参与实现者审查；真实平台检查由获授权验收者执行，缺项保持 blocked/not_run。
7. 向用户展示有证据的完成范围、未决及风险；用户决定验收／合并。不得平台 auto-merge 或自动发布。
8. 合并或交付获准后核远端精确 SHA 和产物，不把本地 clean 当远端成功；M1 或 release 另开明确授权。
